# README 写法

README 是项目入口，只给人读：说明用途、特点、运行条件、设置方式和文档导航；不写成任务交接、调试记录或执行报告。需要 Agent 逐步执行的安装、配置与验收步骤放在单独的手册里，例如 `SETUP.md`。

## 结构

按仓库类型选栏目，不套固定模板，也不要求固定篇幅；涉及本机配置、后台服务或账号登录时，安装与运行步骤按下文「设置方法」处理：

| 仓库类型 | 主体 | 按需补充 |
|---|---|---|
| 服务或应用 | 定位、特点、环境、设置方法、配置、文档导航 | 确有部署包时写部署，确有许可文件时写许可 |
| 命令行工具 | 用途、特点、安装、典型命令、输入输出、配置 | 长任务控制、脚本调用与退出码 |
| 库 | 用途、安装、调用示例、接口文档入口 | 兼容版本 |
| 多仓协作总仓 | 组件组成、系统关系、文档导航 | 不虚构一条能装好全部组件的命令 |
| 兼容维护仓 | 维护定位、现存接口、安装与维护 | 指明新产品名称，不宣称已迁移 |

README 一律中英两份（用户明确只要单语时除外）：中文 `README.md` 为主版本，英文 `README.en.md` 逐节对应、表格行列一致、标题语义一致，语句地道而非逐字直译。两份顶部互相链接：中文版 `中文 | [English](README.en.md)`，英文版 `[中文](README.md) | English`。改任何一份都同步另一份；链接目标与当前 README 语言不同时标注语言，如英文版链到中文文档时注 “(Chinese)”。

对照范例：codex-flow V0.2.0 的 [README.md](https://github.com/Eason412/codex-flow/blob/V0.2.0/README.md) 与 [README.en.md](https://github.com/Eason412/codex-flow/blob/V0.2.0/README.en.md)。

## 开头

- 首段由一句加粗的结果式标语和一两句说明组成，优先写目标读者的主要用途与核心收益，不以类别描述（“X 是一个……工具”）或实现流程起笔。
- 影响读者选用的关键前提在开头用一个 ⚠️ 提示块写明；完整依赖和特定模式的条件放在相关栏目或设置手册。
- 理解首段必需的术语用一两条短定义说明，其他技术概念不在开头引入。
- 版本信息压缩为一行：当前版本、更新日志、已发布版本；有上游来源或二次开发关系时在同一处注明并链接。

## 特点

- 「特点」即卖点，回答“为什么用它”：写本项目已实现、相对常见方案有差异价值的能力。具体的兼容支持、个人设置、写入保护等机制都可以是卖点；同类项目普遍具备的（有测试、真实调用验收、有安装手册、文档齐全）不算。
- 从已实现能力中挑出影响读者选用的差异价值，按核心收益组织，一般三到五条；同一收益下的机制合并成一条，保护或兼容机制只有形成独立卖点时才单列。
- 每条用一个 emoji、加粗的名词化标题和一两句具体说明。标题写读者得到的结果，不写实现对象：「新模型自动同步」而非「实时模型目录」，「差异化个人设置」而非「独立个人偏好」。正文先说明读者获得的结果或省去的操作，再用必要的机制解释；需要对比时再交代常见做法的问题。

## 支持范围

- 支持范围影响读者是否选用时，单列一节并配简表，如「模型系列｜示例模型｜接入方式」。先按实际机制说明整体范围（如“上游支持的模型均可接入”），再列有出处的常见产品示例；接入方式按有依据的账号、套餐或接口类型分行，不用“对应路由”等泛称；局部接法不写成全部支持方式。
- 区分整体接入范围与具体功能兼容性：只保留影响选用的必要条件，验收方法和个别路由问题链接到正式文档。不加实测记录列、测试版本或日期脚注，兼容问题由使用者提 PR；兼容版本按可核实的依据写。

## 设置方法

- README 不设“快速开始”栏目。设置涉及本机配置、后台服务或账号登录的项目，执行步骤写进面向 Agent 的手册（默认 `SETUP.md`，仓库尚无时一并新建）：按顺序编号，每步写命令、成功判据，以及安装软件、修改配置、重启服务、消耗额度前需征得用户同意的操作，任何一家的 Agent 都能照做。
- README 的「设置方法」只写四样：由 Agent 读取该手册完成设置、完成后的必要动作（如重启）、需用户亲自完成的事项（如账号登录）、常用个人设置表。不枚举 Agent 产品，不转述手册的步骤、目录或审批规则，不给示例提示词。
- 库和一条命令即可运行的工具在「安装」「用法」栏目给最常用的路径，写清工作目录、前置条件和成功时能看到的结果。发行包与源码、Mock 与真实模型、单机与服务器分开写；次要变体和完整参数链接到正式文档。

## 工作原理

- 优先用一张流程图（`text` 代码块）加一张「组成｜作用」表，只保留理解组成、数据流和方案选择所需的信息；有多种接入方式时再加一张对照表。
- 解析器、请求头、保护条件等实现细节链接到正式文档，不在 README 展开。

## 表格

每张表回答读者的一个问题：支持哪些、由什么组成、选哪种方式、在哪里设置、文件在哪。多项同类信息优先用简表；不因篇幅或版面删除表格，也不改成长段落，拥挤时只改写单元格。

- 两到四列；表头用名词，如「组成｜作用」「接入方式｜适用平台｜特点」「设置项｜位置｜说明」「路径｜用途」。
- 首列是短名词；单元格写名词短语或一句短句，一般不超过一行（约 40 个汉字），同列各行句式与长度相近，并列项用顿号。
- 单元格不放 ✅、“已验证”一类状态标记，也不放多句解释或排查记录。“（默认）”这类影响选择的条件可用括注，路径表的首列可放链接；其余补充放在表下一句或正式文档。
- 示例列用有出处的产品名称。设置表写默认文件位置和用户会调整的字段，格式字段、路径变体与完整参数链接到参考文档；同一位置的设置可合并，保留读者需要区分的用途。模型 ID、命令、路径和字段用代码格式。

反例（一格三句，夹带限制与旁支链接）：「`probe-multi-agent --models <id>`｜经透明代理发送合成任务，检查正文是否送达；不等于原生 spawn 验收，后者见 [……]」。
正例（首列短名词，单元格一句话）：「透明代理｜本机服务，接收 Codex 请求，替换为 CPA 密钥后原样转发」。

## 文风

- 说明性内容分点，每点用“**小标题**：一两句完整、平实的陈述”，不堆成大段；标题用名词或名词短语。首段标语和 ⚠️ 提示块保持段落，流程图与表格照旧，表格不改成分点或长段落。
- 名词化、书面化：标题与条目标题用名词或名词短语（「设置方法」而非「如何设置」，「特点」而非「为什么用它」）。正文用完整、平实的陈述句，不堆叠名词；否定式改写成正向结果（「主配置保持不变」而非「不会把主配置改坏」）；不用第二人称，也不用“一键、搞定、轻松、放心”一类口语和营销腔。
- emoji：每个二级标题和特点各条各用一个贴合内容的 emoji，同一 emoji 不重复使用，正文段落与表格内不用。常用对应：特点 ✨、支持范围 🧩、工作原理 ⚙️、设置方法 🚀、仓库结构 📁、贡献须知 🤝、许可证 📄、前提提示 ⚠️。
- 只引入读者理解用途和设置所需的术语，首次出现处说明含义，或在同页后文定义且此处不依赖其含义；命令、字段、状态和模型 ID 保持原样。

## 内容

- 命令来自真实的解析器、脚本或包配置；缺证据的步骤不写成可复制命令。不能为了简短省掉必要的 worker、数据目录或权重等启动条件。
- 必要限制放在相关能力或配置旁边，不在每段追加免责声明。设计提案标明状态，不当作已实现能力写进特点或表格。
- 保留已核实的项目来源、第三方署名与许可证入口；不虚构克隆地址、徽章、维护者、许可证或社区承诺。内部项目不默认加贡献指南、Issues 或赞助章节，内部托管平台不改写成 GitHub。公开仓库的贡献须知写提交 PR 时的注意事项，完整要求链接到 `CONTRIBUTING.md`。

## 链接

- 优先用本仓相对链接；不出现个人绝对路径、本机备份或任务记录目录。只存在于某台机器上的相邻仓库，写仓库标识和路径说明，或已核实的托管链接。
- 被 Git 忽略的目标不是可分发链接；获准把正式文档纳入 Git 时先检查隐私和来源再暂存，否则换成已跟踪的资料或说明缺口，不擅改忽略规则。

## 文档边界

正式文档沿用项目已有的组织方式，放系统说明、架构、接口与 CLI 参考、配置和开发验证；任务记录、临时方案和排查过程留在项目的任务资料里。任务完成后只把确认的稳定行为写进正式文档。

写文档不自动执行安装、付费模型调用、真实数据写入或服务启动。大幅重构且有隐含前提时，可以请一位没有背景的读者按成稿找入口、条件和成功结果，只修真实缺口。

## 交付核对

- 动笔前列出本次用户要求与项目偏好（定位、目标读者、示例取舍等，规范无法推导的内容向用户或项目资料获取），完成后逐项对照，并检查有无未要求的改动，如标题改名、链接或 emoji 被删。委派时把这些要求逐条编号交给执行者。
- 正文与表格中的能力、前提、支持范围和示例都核对出处；区分本项目实现、上游能力与当前部署结果，只写影响选择的必要条件。跨组件结论沿调用链核对：例如写“上游必须支持某协议”前，先确认中间层是否做了转换；核实不了的不扩大表述。

## 结构检查

使用 `check_readme.py --repo <仓库> --pair README.md README.en.md --json` 同时检查两份文档的本地链接、Markdown 锚点与双语结构；明确只需单语时用 `--file`。加 `--require-tracked` 可检查链接目标是否已进入 Git 索引。审阅时禁用字节码写入，实验产物放临时目录。

- **error**：标题数量与层级序列、表格数量与各行列数、本地链接目标集合、图片引用集合及顶部语言切换链接不一致；除 `text`、无语言标记、`json`、`yaml` 外的围栏代码块按顺序比较语言标记与内容。两组围栏分别比较，避免可翻译块的增删影响命令块的配对。
- **行内代码**：按多重集合比较，允许语序不同；`<模型>` 与 `<model>` 归一为 `<*>`，`[任务名]` 与 `[task]` 为 `[*]`，`{{task:名字}}` 与 `{{task:name}}` 为 `{{task:*}}`，阶段引用 `{{phase:标题}}` 同理为 `{{phase:*}}`。严重程度按归一后的内容判断，原文只用于展示：未匹配的含中文代码记 warning；一侧未匹配的 ASCII 代码数不多于另一侧未匹配的含中文代码数时，也记 warning（视为翻译后的示例名称），其他未匹配标识记 error。一侧用普通引号、另一侧用行内代码的示例名称，仅当成对 JSON 的同一位置 `name` / `title` / `label` 能确认中英映射且中文名称确实出现在对侧正文引号中时降为 warning，并报告该正文位置；不凭任意正文相似性放过命令差异。
- **方括号占位符**：仅归一独立的单个名称（Unicode 字母或下划线起首，后接字母、数字、下划线或连字符），如 `[任务名]` / `[task]`。紧跟标识符或右括号 `)`、`]`、`}` 的方括号视为下标；带引号、逗号、数字字面量或表达式的内容不归一，例如 `config["timeout"]`、`["README.md"]`、`[a, b]`、`[10]`。
- **warning**：可翻译围栏的语言标记或内容差异，以及上述示例名称差异。报告提供每侧文件、行号和内容；缺失项定位到另一侧的实际位置，缺顶部切换链接定位到缺失文件首行。`ok` 只由 error 决定，warning 留给人工核对；结构对齐不证明翻译语义或业务内容正确。
- **目标与锚点**：本地链接比较解析后的文件目标，忽略查询与 fragment 的语言差异；本次两份文件和实际存在的 `name.md` / `name.en.md` 视为成对目标。锚点另按每份文档独立检查：标题取渲染文字并排除图片 alt，小写后按 github-slugger 的字符口径过滤：保留 Unicode 字母（L*）、组合符号（M*）、十进制数字（Nd）、字母数字（Nl）、连接标点（Pc，含下划线）和字母型带圈/方框符号，以及 ASCII 空格、连字符；其他字符去掉，空格换连字符，重名依次加 `-1`、`-2` 并避开全部已生成 slug；HTML `id` 与 `<a name>` 按原始大小写匹配，fragment 先百分号解码。非 Markdown 文件不查锚点。顶部指首个二级及以下标题之前的引言区，未使用的引用定义不算语言切换链接。图片集合保留查询与 fragment，避免把不同图像变体视为同一引用。

字符表冻结为审查夹具所用的 Unicode 13 口径，离线检查不随 Python 的字类数据升级而改变；例如 `‿`、`ⓐ` 保留，`²`、`¼`、emoji 去掉，Unicode 13 的 CJK 扩展 G 保留，更晚新增的字符不保留。表位于 `scripts/slug_chars.json`，由原创的 `scripts/generate_slug_chars.py` 从 CPython 3.9 内置 Unicode 数据生成；维护时可在临时目录用 `PYTHONDONTWRITEBYTECODE=1 uv run /path/to/generate_slug_chars.py > slug_chars.json` 重建并核对，运行检查只需 `markdown-it-py`。多行链接、图片和 code span 的位置按解析消耗的源码计算，包括目标与 title 中未渲染的换行。

项目已有 markdownlint、cog、lychee 或外链检查工具时可以接入；本 Skill 的脚本保持零网络、只读、单依赖，不内置这些工具。
